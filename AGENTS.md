# AGENTS.md

## 1. Назначение проекта

Проект представляет собой локальный dashboard, работающий в браузере Microsoft Edge. В рамках тестирования использовать Google Chrome.

Dashboard предназначен для отображения и обработки производственных данных, поступающих из Excel.

Excel и VBA отвечают за подготовку и экспорт исходных данных.

Вся бизнес-логика, обработка данных, расчёты и визуализация выполняются на стороне браузера.

---

## 2. Среда выполнения

Проект должен работать локально на рабочем компьютере.

Основной и единственный целевой браузер:

* Microsoft Edge.

Проект не должен требовать:

* установки дополнительного программного обеспечения;
* локального web-сервера;
* Node.js;
* npm;
* Python;
* внешней базы данных;
* backend-сервера;
* облачной инфраструктуры.

Dashboard должен запускаться непосредственно через локальный `index.html`.

Основной сценарий запуска:

```text
file:///.../dashboard/index.html
```

Все архитектурные решения должны учитывать ограничения локальной работы через `file://`.

---

## 3. Источники данных

Данные для dashboard формируются внешними Excel-книгами с помощью VBA.

Excel/VBA не содержит бизнес-логику dashboard.

Excel/VBA и механизм формирования snapshot находятся за границей ответственности данного проекта.

---

## 4. Формат snapshot-файлов

Каждый логический источник данных имеет отдельный JavaScript-файл.

Пример:

```text
data/
├── production11.js
├── quality12.js
└── plan13.js
```

Каждый источник создаёт собственную глобальную переменную в `window`.

Пример:

```javascript
window.Production11Data = {
    generatedAt: "2026-09-09T18:40:00",
    rows: [
        ["2026-09-09T17:01:11", "ABC123"],
        ["2026-09-09T17:02:25", "ABC124"]
    ]
};
```

Общий принцип:

```javascript
window.<SourceName>Data = {
    generatedAt: "...",
    rows: [...]
};
```

### generatedAt

`generatedAt` содержит дату и время создания snapshot.

Он является метаданными источника и не является производственной записью.

### rows

`rows` содержит непосредственно данные источника.

Конкретная структура строки зависит от типа источника.

Бизнес-интерпретация содержимого `rows` выполняется на стороне браузерного приложения.

---

## 5. Фиксированный контракт входных данных

Формат входных данных является фиксированным внешним контрактом проекта.

Codex должен исходить из того, что snapshot-файлы поступают в установленном формате и этот формат не является предметом проектирования или изменения в рамках dashboard-проекта.

Описанный в этом документе формат:

```javascript
window.<SourceName>Data = {
    generatedAt: "...",
    rows: [...]
};
```

является данностью.

Codex не должен:

* предлагать изменение VBA для упрощения реализации dashboard;
* проектировать VBA-код экспорта;
* переписывать VBA-код экспорта;
* предлагать перенести обработку или бизнес-логику из браузера в Excel/VBA;
* изменять структуру snapshot ради удобства JavaScript-кода;
* считать изменение источника данных допустимым способом решения задачи.

Если полученные данные необходимо:

* интерпретировать;
* преобразовать;
* нормализовать;
* фильтровать;
* группировать;
* агрегировать;

это должно выполняться на стороне браузерного приложения в соответствующем архитектурном слое.

Если поставленная задача объективно не может быть выполнена с имеющимися входными данными, Codex должен остановиться и сообщить:

1. каких именно данных недостаточно;
2. почему без них задача не может быть выполнена;
3. какая часть задачи из-за этого заблокирована.

Codex не должен самостоятельно проектировать новый формат snapshot или изменение VBA в качестве решения этой проблемы.

Всё, что находится до готового `data/*.js`, находится за границей полномочий Codex в данном проекте.

## 6. Имена источников

Имя источника используется при создании глобального JavaScript-объекта.

Для имён источников применяется ограниченный безопасный формат:

* латинские буквы `A-Z`, `a-z`;
* цифры `0-9`;
* символ `_`;
* первый символ должен быть буквой.

Не использовать:

* пробелы;
* дефисы;
* точки;
* кириллицу;
* специальные символы.

Примеры допустимых имён:

```text
Production
Quality
Production11
Quality12
Production_Line11
```

Пример результата:

```javascript
window.Production11Data
```

## 8. index.html

`index.html` отвечает только за основной DOM-каркас страницы.

В нём должны находиться:

* основные контейнеры dashboard;
* семантическая структура страницы;
* точки подключения визуальных компонентов;
* подключения CSS и JavaScript.

`index.html` не должен содержать бизнес-логику.

По возможности в нём также не должна находиться логика:

* загрузки snapshot;
* обработки данных;
* расчётов;
* периодического обновления;
* построения widgets.

JavaScript-код должен находиться в соответствующих JavaScript-модулях проекта.

Принцип:

```text
index.html = где находится элемент
```

---

## 9. dashboard.css

`css/dashboard.css` отвечает за внешний вид dashboard.

В нём определяются:

* layout;
* размеры;
* сетки;
* отступы;
* типографика;
* оформление карточек;
* состояния элементов;
* оформление таблиц;
* оформление графиков и других визуальных компонентов.

CSS не должен определять бизнес-логику приложения.

Принцип:

```text
dashboard.css = как выглядит элемент
```

---

## 10. app.js

`js/app.js` является точкой запуска, координатором приложения и управляющим потоком данных между слоями.

Он отвечает за:

* инициализацию dashboard;
* запуск источников данных;
* координацию обновлений;
* получение результатов от `sources/`;
* определение дальнейшего сценария обработки;
* передачу данных в необходимые функции `core/`;
* получение результатов расчётов от `core/`;
* передачу подготовленных результатов в `widgets/`;
* управление общим жизненным циклом приложения.

`app.js` определяет, что, когда и в какой последовательности должно быть выполнено.

При этом `app.js` не должен самостоятельно выполнять работу специализированных слоёв.

Сложные расчёты должны выноситься в `core/`.

Логика получения конкретного источника должна находиться в `sources/`.

Логика отображения конкретного элемента должна находиться в `widgets/`.

Принцип:

```text
app.js = управляет потоком и определяет, что и когда должно быть выполнено
```

---

## 11. sources/

Каталог:

```text
js/sources/
```

содержит код получения данных из внешних snapshot-файлов.

Source является адаптером между внешним файлом данных и `app.js`.

Source может отвечать за:

* загрузку JavaScript snapshot;
* повторную загрузку snapshot;
* обход browser cache при необходимости;
* проверку существования ожидаемой глобальной переменной;
* базовую проверку структуры snapshot;
* получение `generatedAt`;
* получение `rows`;
* определение факта обновления источника;
* обработку ошибок загрузки.

Source возвращает результат своей работы `app.js`.

Source не должен:

* самостоятельно определять дальнейший сценарий обработки;
* самостоятельно вызывать `core/`;
* самостоятельно вызывать `widgets/`;
* заниматься визуальным отображением;
* выполнять бизнес-расчёты, не относящиеся непосредственно к получению и проверке источника.

Принцип:

```text
source = как получить данные
```

## 12. core/

Каталог:

```text
js/core/
```

содержит бизнес-логику и общие вычислительные механизмы dashboard.

Здесь могут находиться:

* расчёты производительности;
* работа со временем;
* логика смен;
* фильтрация данных;
* группировка данных;
* агрегация;
* преобразование исходных строк;
* работа с настройками;
* локальное состояние;
* другие функции, не зависящие от конкретного визуального представления.

Core получает данные для обработки и возвращает результат расчёта.

Core не должен:

* самостоятельно управлять общим потоком приложения;
* самостоятельно загружать snapshot-файлы;
* самостоятельно вызывать widgets;
* заниматься непосредственным построением интерфейса.

Функция из `core/` должна по возможности:

```text
получить данные
      ↓
выполнить расчёт
      ↓
вернуть результат
```

Она не должна знать, каким цветом, размером или в каком месте страницы результат будет показан.

Принцип:

```text
core = что означают данные и что из них нужно вычислить
```

### Словарь пользовательского интерфейса

Тексты, которые видит пользователь, хранятся в отдельном файле:

```text
js/core/dictionary.js
```

Словарь содержит одинаковые ключи для поддерживаемых языков и предоставляет
данные через глобальный объект `window.DashboardDictionary`, совместимый с
локальным запуском через `file://`.

В словаре могут находиться только пользовательские названия, подписи,
сообщения и названия состояний.

Словарь не должен:

* содержать бизнес-логику;
* выбирать активный язык;
* самостоятельно изменять DOM;
* обращаться к sources или widgets.

```text
js/widgets/
```

* отобразить значение;

Widget не должен:

* самостоятельно вызывать `sources/`;

Widget по возможности не должен напрямую обращаться к:

```javascript
window.Production11Data
```

Принцип:

```text
widget = как показать конкретный результат
```

## 14. data/

Каталог:

```text
data/
```

содержит snapshot-файлы, создаваемые внешними источниками.

Например:

```text
data/
├── production11.js
├── quality12.js
└── plan13.js
```

Файлы из `data/` рассматриваются как входные данные приложения.

Dashboard не должен зависеть от ручного редактирования этих файлов.

Snapshot-файлы являются внешними входными данными и не должны изменяться кодом dashboard.

## 15. Направление ответственности и управление потоком

`app.js` является центральным координатором потока данных.

Базовая схема:

```text
data
 ↓
sources
 ↓
app.js
  │
  ├──→ core
  │      │
  │      ↓
  │   результат
  │      │
  ←──────┘
  │
  ↓
widgets
 ↓
DOM
```

`source` получает данные и возвращает их `app.js`.

`app.js` решает, требуется ли дальнейшая обработка и какие функции `core/` необходимо вызвать.

`core/` выполняет расчёты и возвращает результат `app.js`.

`app.js` передаёт подготовленные результаты соответствующим widgets.

Widgets отображают полученные результаты в DOM.

Упрощённая модель ответственности:

```text
data/
    Какие данные были экспортированы?

sources/
    Как получить эти данные?

app.js
    Что делать с полученными данными,
    что вызвать и в какой последовательности?

core/
    Что означают данные и что нужно рассчитать?

widgets/
    Как показать переданный результат?

index.html
    Где находится результат?

dashboard.css
    Как результат выглядит?
```

---

## 16. Независимость слоёв

Следует избегать прямых зависимостей, нарушающих управление потоком через `app.js`.

Нежелательная схема:

```text
widget
  ↓
window.Production11Data
```

Также нежелательны схемы:

```text
source → core
source → widget
core → widget
widget → source
widget → core
```

Предпочтительная схема:

```text
Production11Data
      ↓
production source
      ↓
    app.js
      │
      ├──→ production core
      │         │
      │         ↓
      │      результат
      │         │
      ←─────────┘
      │
      ↓
    widget
```

Специализированные слои выполняют свою работу и возвращают результат координатору.

`app.js` управляет взаимодействием между ними.

Бизнес-расчёты не должны выполняться непосредственно внутри `index.html`, `dashboard.css` или source.

---

## 17. Расширение источников

Архитектура должна позволять добавлять новые источники без изменения общего принципа управления потоком.

Для одного источника:

```text
production11.js
       ↓
production source
       ↓
     app.js
       │
       ├──→ production core
       ├──→ worktime core
       └──→ другие необходимые core-функции
       │
       ↓
     widgets
```

При появлении нескольких источников:

```text
production11.js → production source ─┐
                                     │
quality12.js    → quality source ────┼→ app.js
                                     │    │
plan13.js       → plan source ───────┘    ├──→ core
                                          │
                                          └──→ widgets
```

Каждый source отвечает только за получение своего источника.

`app.js` определяет, какие данные и расчёты должны использоваться совместно.

Добавление нового источника не должно требовать изменения формата уже существующих snapshot-файлов.

---

## 18. Один источник — один snapshot

Базовый архитектурный принцип проекта:

```text
один логический источник данных
        =
один snapshot-файл
        =
одна уникальная window.*Data переменная
```

Например:

```text
production11.js
→ window.Production11Data

quality12.js
→ window.Quality12Data

plan13.js
→ window.Plan13Data
```

Это позволяет независимо:

* обновлять источники;
* проверять их состояние;
* отслеживать время генерации;
* обрабатывать ошибки;
* расширять dashboard.

---

## 19. Обновление данных

Snapshot-файлы могут изменяться во время работы dashboard.

Архитектура должна поддерживать автоматическую повторную загрузку источников без ручного обновления всей страницы.

`app.js` координирует процесс обновления.

Source отвечает за получение и проверку конкретного snapshot.

При этом необходимо разделять:

```text
проверку/получение нового snapshot
```

и:

```text
обработку данных и перерисовку dashboard
```

Отсутствие изменений в источнике не должно без необходимости приводить к повторным бизнес-расчётам и перерисовке интерфейса.

Конкретный механизм определения изменения snapshot может развиваться отдельно.

Возможные метаданные или механизмы контроля, такие как `generatedAt` или hash содержимого, не должны жёстко связывать бизнес-логику с механизмом загрузки файла.

---

## 20. Принцип минимальной ответственности Excel/VBA

Excel/VBA является поставщиком данных, а не движком dashboard.

VBA выполняет только операции, необходимые для формирования корректного snapshot.

Не переносить в VBA расчёты только потому, что исходные данные находятся в Excel.

Предпочтительная схема:

```text
Excel/VBA
    ↓
минимальные исходные данные
    ↓
browser
    ↓
business logic
    ↓
visualization
```

Формат snapshot является внешним контрактом и не изменяется в рамках dashboard-проекта.

# Правила работы Codex

## 21. Основной принцип самостоятельности

Codex имеет право самостоятельно выбирать способ реализации поставленной задачи в пределах существующей архитектуры.

Codex не имеет права самостоятельно:

* расширять scope поставленной задачи;
* изменять архитектурные решения проекта;
* изменять внешние контракты проекта;
* реализовывать функциональность, которая не была запрошена.

Основной принцип:

```text
Codex свободен внутри поставленной задачи,
но не свободен расширять саму задачу.
```

Поставленная пользователем задача определяет границу изменений.

---

## 22. Минимальный scope изменений

Перед началом изменений Codex должен определить минимальный набор файлов и компонентов, необходимых для выполнения задачи.

Следует предпочитать решение:

* с минимальным количеством изменяемых файлов;
* без изменения соседней функциональности;
* без ненужного рефакторинга;
* без подготовки архитектуры «на будущее»;
* без добавления абстракций, которые не нужны текущей задаче.

Если задача может быть выполнена в существующей архитектуре, она должна быть выполнена в существующей архитектуре.

Не следует перестраивать проект только потому, что другой вариант кажется более универсальным или архитектурно интересным.

---

## 23. Что Codex может делать самостоятельно

В пределах явно поставленной задачи Codex может самостоятельно:

* выбирать имена локальных функций и переменных;
* выбирать внутреннюю реализацию функции;
* разбивать большую новую функцию на несколько небольших;
* добавлять необходимые локальные вспомогательные функции;
* исправлять очевидные синтаксические ошибки в непосредственно изменяемом коде;
* добавлять минимальную обработку ошибок, необходимую для корректной работы поставленной задачи;
* выполнять небольшие локальные изменения, не меняющие архитектуру и внешние контракты.

Такие решения не требуют отдельного согласования, если они не расширяют scope задачи.

---

## 24. Что требует согласования

Codex должен остановиться и получить решение пользователя до выполнения изменения, если требуется:

* изменить архитектуру проекта;
* изменить ответственность существующего слоя;
* создать новый архитектурный слой;
* изменить структуру каталогов проекта;
* изменить формат snapshot;
* изменить интерфейс между `sources/`, `app.js`, `core/` и `widgets/`;
* изменить общий механизм загрузки данных;
* изменить общий механизм обновления данных;
* добавить стороннюю библиотеку или framework;
* добавить новую внешнюю зависимость;
* выполнить существенный рефакторинг существующего рабочего кода;
* удалить существующую функциональность;
* изменить поведение компонентов, не относящихся к текущей задаче.

В такой ситуации Codex должен:

1. остановиться до спорного изменения;
2. объяснить, почему текущая задача требует выхода за установленную границу;
3. указать, какие файлы или архитектурные решения необходимо затронуть;
4. предложить минимально необходимое изменение;
5. дождаться решения пользователя.

## 25. Что запрещено без прямого задания

Codex не должен самостоятельно:

* переписывать соседние файлы «заодно»;
* выполнять косметический рефакторинг вне текущей задачи;
* удалять рабочий код, который не мешает выполнению задачи;
* переименовывать существующие файлы без необходимости;
* перемещать существующие файлы;
* менять структуру проекта;
* добавлять будущую функциональность;
* создавать универсальные системы для гипотетических будущих требований;
* добавлять framework или библиотеку ради удобства;
* добавлять Node.js, npm, Python, сервер или backend;
* изменять входные snapshot-файлы;
* проектировать изменение VBA;
* переписывать VBA;
* переносить бизнес-логику в Excel/VBA;
* менять установленный формат входных данных.

Фраза «так будет лучше архитектурно» сама по себе не является основанием для выхода за scope задачи.

## 26. Работа с внешним контрактом данных

Snapshot является входом в систему.

Для Codex граница проекта выглядит так:

```text
Excel / VBA
     ↓
готовый snapshot
══════════════════════ граница проекта
     ↓
data/*.js
     ↓
dashboard
```

Codex работает ниже этой границы.

Если формат данных неудобен для конкретного расчёта, Codex должен адаптировать браузерную часть проекта к установленному формату.

Неудобство обработки данных не является основанием для изменения snapshot или VBA.

Если необходимых данных в snapshot физически нет, Codex должен сообщить об этом пользователю и остановиться в заблокированной части задачи.

## 27. Обнаружение проблем вне задачи

Во время выполнения задачи Codex может обнаружить ошибку, потенциальную проблему или возможность улучшения в другом участке проекта.

Если эта проблема не блокирует текущую задачу, Codex не должен исправлять её самостоятельно.

Codex должен:

1. завершить поставленную задачу;
2. сообщить об обнаруженной проблеме отдельно;
3. указать, что проблема не исправлялась, поскольку находится вне scope текущей задачи.

Пример поведения:

```text
Выполнено:
- изменён production-source.js;
- добавлена проверка generatedAt.

Дополнительно обнаружено:
- в app.js возможен повторный запуск таймера.
- не исправлял, так как это вне текущей задачи.
```

Если обнаруженная проблема блокирует выполнение задачи, применяется правило согласования: Codex останавливается и сообщает пользователю о препятствии.

## 28. Запрет скрытого расширения задачи

Codex не должен интерпретировать конкретную задачу как разрешение на общую переработку связанной подсистемы.

Например, задача:

```text
Добавить widget статуса Production.
```

не означает разрешение:

```text
переписать source loader;
создать event bus;
создать глобальный state manager;
создать registry widgets;
изменить формат snapshot;
реорганизовать app.js.
```

Для выполнения задачи сначала необходимо искать минимальное решение в рамках существующей архитектуры.

## 29. Рефакторинг

Рефакторинг допустим самостоятельно только тогда, когда он:

* локален;
* непосредственно необходим для выполнения текущей задачи;
* не меняет внешнее поведение;
* не меняет архитектуру;
* не затрагивает несвязанные компоненты.

Существенный рефакторинг должен рассматриваться как отдельная задача и требует согласования.

Codex не должен использовать небольшую функциональную задачу как повод для общего рефакторинга проекта.

## 30. Новые файлы

Создание нового файла допустимо без отдельного согласования, если:

* файл непосредственно необходим для поставленной задачи;
* его расположение однозначно определяется существующей архитектурой;
* он не создаёт новый архитектурный слой.

Например, если пользователь явно просит создать новый widget, создание соответствующего файла в:

```text
js/widgets/
```

является нормальной частью задачи.

Создание новой директории, нового слоя или новой системы организации файлов требует согласования, если это не было прямо указано пользователем.

## 31. Зависимости

Проект должен оставаться самодостаточным и работать локально.

Codex не должен самостоятельно добавлять:

Предпочтение отдаётся возможностям стандартных:

* HTML;
* CSS;
* JavaScript;

## 33. Поведение при неоднозначности

Если существует несколько технических вариантов, но все они:

* находятся внутри scope задачи;
* соответствуют `AGENTS.md`;
* не меняют архитектуру;
* не меняют внешний контракт;

Codex может самостоятельно выбрать наиболее простой вариант.

Если выбор затрагивает архитектуру, внешний контракт, структуру проекта или будущий способ развития проекта, решение должен принимать пользователь.

При сомнении между:

```text
локальное техническое решение
```

и:

```text
архитектурное решение
```

Codex должен считать решение архитектурным и запросить согласование.

## 34. Не проектировать будущее без задачи

Архитектура должна оставаться расширяемой, но это не означает необходимость заранее реализовывать расширения.

Codex не должен добавлять код только потому, что он потенциально может пригодиться позже.

Не создавать без текущей необходимости:

* универсальные registries;
* plugin systems;
* event buses;
* дополнительные abstraction layers;
* универсальные factories;
* сложные configuration systems;
* инфраструктуру для ещё не существующих источников;
* инфраструктуру для ещё не существующих widgets.

Сначала реализуется текущая потребность.

Расширение выполняется тогда, когда появляется реальная задача.

## 36. Отчёт после выполнения

* как был проверен результат;

Не требуется подробно пересказывать весь написанный код, если пользователь этого не просил.

## 37. Приоритет инструкций проекта

При работе с кодовой базой Codex должен руководствоваться следующей последовательностью:

```text
явная текущая задача пользователя
          ↓
AGENTS.md
          ↓
существующая архитектура и контракты проекта
          ↓
существующий рабочий код
          ↓
локальное техническое решение Codex
```

Текущая задача пользователя определяет, **что нужно сделать**.

`AGENTS.md` определяет, **в каких границах это можно делать**.

Существующая архитектура определяет, **куда относится новый код**.

Codex самостоятельно выбирает только детали реализации, которые остаются внутри этих границ.

---

## 38. Основной архитектурный принцип

При добавлении нового кода сначала определить его ответственность.

Если код отвечает на вопрос:

```text
"Как получить данные?"
```

он относится к `sources/`.

Если:

```text
"Как обработать или рассчитать данные?"
```

он относится к `core/`.

Если:

```text
"Что делать, когда это выполнить и как связать части приложения?"
```

он относится к `app.js`.

Если:

```text
"Как показать результат?"
```

он относится к `widgets/`.

Если:

```text
"Где элемент находится?"
```

он относится к `index.html`.

Если:

```text
"Как элемент выглядит?"
```

он относится к `dashboard.css`.

Если Codex может выполнить задачу без изменения архитектуры, внешних контрактов и несвязанного кода — он должен выполнить её самостоятельно минимальными изменениями.

Если для выполнения задачи необходимо выйти за эти границы — Codex должен остановиться и получить решение пользователя.

Не расширять задачу самостоятельно.
